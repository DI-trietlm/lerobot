VLA Harness Architecture

Kiến trúc hybrid server/client cho SmolVLA deployment: VLA vẫn là controller chính, harness chỉ giám sát, chặn lỗi rõ ràng, can thiệp rất nhỏ khi kẹt, rồi bắt buộc flush/re-infer để tránh bất đồng bộ chunk.

Repo: LeRobot RTC stack Runtime config: runtime_configs/*.json Code: src/lerobot/vla_harness/ Principle: data-derived, not task-hardcoded

1. Điều ta đang giải quyết

Lỗi runtime hiện tại không nên hiểu đơn giản là "robot cứ về safe pose". Dataset cho thấy folded/safe-like pose có thể là waypoint hợp lệ trước approach/grasp. Vấn đề nguy hiểm hơn là mất phase progression: policy có lúc đi vào vùng prepare/folded nhưng không thoát tiếp sang approach/grasp/pour, hoặc gửi hành động phá task như mở gripper sai thời điểm.

Vì vậy harness không được hard-code "cấm về safe pose". Nó cần phát hiện stuck, action ngoài phân phối, invariant bị phá, rồi can thiệp tối thiểu từ chính phân phối demonstration.

2. Sơ đồ tổng thể

Offline Dataset Profile Mine mode, invariant, speed envelope, rescue snippets từ dataset train. Output: harness_profile.json.
Server Harness Gắn gần policy: validate raw/postprocessed chunk, build metadata, đề xuất micro-rescue, nhận intervention từ client.
Client Harness Gắn gần robot: final guard, tracking monitor, speed clamp, hard invariant guard, clear queue khi can thiệp.
Sync + Trace Intervention ledger, chunk id, queue invalidation, re-infer request, trace JSONL.
Dataset profile -> server validation -> client execution guard -> intervention -> flush/re-infer

3. Hybrid server/client: đặt cái gì ở đâu?

Server side

Nơi biết policy, raw chunk, postprocessor và profile dataset.

  • Load harness_profile.json.
  • Validate chunk trước khi gửi sang client.
  • Estimate mode từ state/action history nếu profile đủ tốt.
  • Đánh dấu invariant/speed violations trong harness_decision.
  • Đề xuất hoặc thay chunk bằng micro-rescue khi có intervention + stuck context.
  • Nhận intervention event từ client và clear RTC/action queue nếu cần.

Client side

Nơi biết robot thực thi gì thật, tracking error và state sau action.

  • Final guard trước khi gửi action xuống robot.
  • Chặn hard invariant có hậu quả rõ, ví dụ actuator/gripper release sai mode.
  • Clamp spike/velocity ngoài envelope ở mức an toàn.
  • Monitor tracking error: commanded vs actual state.
  • Gửi intervention event về server.
  • Clear local queue và yêu cầu fresh chunk khi intervention mạnh.
Thành phần Ưu tiên đặt chính Lý do
Trace + chunk metadata Server + Client Cần ghép được timeline: raw action, postprocessed chunk, executed action, actual state.
Invariant mining/profile Offline + Server Profile phụ thuộc dataset, mode graph, percentile, support/violation rate.
Hard safety/invariant guard Client final gate Client là nơi cuối cùng trước robot, nên phải có quyền chặn action phá task rõ ràng.
Micro-rescue selection Server proposal, client execution Server chọn snippet theo profile; client execute bounded và flush/re-infer.
Speed envelope Client, có server shadow Speed guard là safety envelope runtime, không phải controller chính.

4. Rule cứng: intervention phải flush/re-infer

Nếu harness sửa action nhưng policy/RTC vẫn tiếp tục chunk cũ, server sẽ tin rằng robot đã đi theo action A trong khi thực tế robot đi theo A'. Đây là nguồn bất đồng bộ rất độc. 

policy planned chunk A
        |
client harness executes modified action A'
        |
actual observation comes from A'
        |
old chunk/aggregator still assumes A  -> drift / confusion / repeated failure

Vì vậy các can thiệp sau phải clear queue/chunk và infer lại:

  • Micro-rescue được execute.
  • Hard invariant clamp/reject, đặc biệt gripper/actuator.
  • Repeated speed clamp vượt ngưỡng max_consecutive_clamps.
  • Stop/hold safety intervention.
  • Server reject/resample chunk.

5. Bốn harness chính

1. Dataset-Manifold Micro-Rescue

Khi stuck, tìm neighbor gần current state trong dataset, chọn snippet ngắn có future progress tốt, execute 0.3-1.0s rồi flush/re-infer.

Không replay cả episode. Không dùng nếu state OOD so với profile.

2. Data-Derived Invariant Guard

Mine invariant theo mode: plateau, no-backtrack, one-shot event, value/velocity envelope. Ví dụ task pouring có thể học rằng một actuator ổn định không nên release sai mode.

Không hard-code tên grasp/hold/release làm logic mặc định.

3. Action Stability + Speed Envelope

Chặn spike, endpoint jump, acceleration/jerk ngoài phân phối. Nếu phải clamp liên tục, coi là failure và re-infer/rescue, không clamp âm thầm mãi.

4. Runtime Sync + Trace Harness

Ghi intervention ledger, raw/postprocessed/executed action, actual state, chunk id, mode estimate, rescue neighbor. Đây là nền để debug mọi lần fail.

6. Ưu tiên bật sắp tới

1

Trace + Sync trước

Bật harness ở chế độ ghi trace, chunk id, intervention ledger, action/server/client logs. Mục tiêu là mọi run fail phải trả lời được: raw policy sai, server postprocess sai, RTC/aggregation sai, hay client execution sai.

Bật ngay
2

Invariant Guard ở shadow mode

Chạy invariant guard không can thiệp trước để đo false positive trên runtime thật. Đặc biệt theo dõi actuator/gripper release sai mode và no-backtrack violation.

Shadow
3

Hard guard chỉ cho invariant confidence cao

Sau khi profile chứng minh support cao và train violation thấp, bật hard guard cho nhóm catastrophic_actuator_release. Mọi hard clamp phải flush/re-infer.

Cẩn trọng
4

Speed envelope shadow, rồi soft clamp giới hạn

Speed envelope dùng để chặn outlier/spike, không dùng để lái robot từng frame. Nếu clamp lặp lại, dừng clamp âm thầm và chuyển sang re-infer/micro-rescue.

Shadow -> soft
5

Micro-rescue sau khi profile được validate

Đây là hướng có giá trị nhất để thoát điểm chết, nhưng chỉ bật khi rescue index có neighbor tốt, max distance hợp lý, cooldown/budget rõ, và trace đầy đủ.

7. Preset config nên dùng

Code hiện có hỗ trợ các preset trong src/lerobot/vla_harness/config.py. Đề xuất rollout:

Giai đoạn Preset Mục tiêu
Ngay bây giờ trace_only Ghi đủ trace, không thay hành vi robot.
Sau khi có profile đầu tiên shadow_all Đo invariant/speed/rescue decision mà chưa can thiệp.
Khi invariant gripper/actuator rất chắc guard_gripper_only Chặn lỗi phá task rõ ràng, vẫn không bật micro-rescue.
Khi speed false positive thấp guard_and_speed Thêm speed envelope như safety guard.
Khi rescue index tốt full_with_micro_rescue Cho phép can thiệp micro để thoát stuck, có cooldown và max rescue budget.

Config shape tối thiểu

{
  "harness": {
    "enable": true,
    "profile_path": "outputs/harness_profiles/pouring_0_3/harness_profile.json",
    "shadow_mode": true,
    "log_dir": "harness_traces",
    "trace": {
      "enable": true,
      "record_raw_chunks": true,
      "record_postprocessed_chunks": true,
      "record_executed_actions": true
    },
    "sync": {
      "enable": true,
      "flush_on_rescue": true,
      "flush_on_hard_clamp": true,
      "flush_on_repeated_speed_clamp": true
    }
  }
}

8. Những điều không nên bật vội

  • Không bật micro-rescue hard nếu chưa có profile/rescue index kiểm chứng trên dataset.
  • Không bật speed clamp hard liên tục như controller thay VLA.
  • Không hard-code "gần safe pose là lỗi"; folded/pre-grasp có thể hợp lệ.
  • Không clamp gripper/action đáng kể mà không clear queue và re-infer.
  • Không rollout guard nếu trace chưa đủ để tái dựng timeline fail.

9. Checklist trước lần robot test tiếp theo

  • Config dùng path mới trong runtime_configs/.
  • Server và client cùng thấy harness.profile_path nếu bật profile-based guard.
  • Bật trace trước, xác nhận sinh server_trace.jsonl và client intervention/runtime logs.
  • Nếu guard can thiệp: kiểm tra event có chunk_id, queue_cleared, requires_reinfer.
  • Sau mỗi run fail, phân tích raw chunk vs executed action trước khi kết luận model/data.
